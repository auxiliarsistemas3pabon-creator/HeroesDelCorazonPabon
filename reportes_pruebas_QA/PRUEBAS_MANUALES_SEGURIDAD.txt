===============================================================================
 GRUPO A — AUTENTICACIÓN Y CONTRASEÑAS
===============================================================================

CAPA 1 · Política de contraseñas
  Qué protege : contraseñas débiles, adivinables.
  Dónde       : backend/config/settings/base.py (AUTH_PASSWORD_VALIDATORS)
  Cómo probar : 1. Inicie sesión y pulse el ícono de llave (Cambiar contraseña).
                2. Como nueva contraseña escriba 12345678 y confírmela.
                3. Repita con "password1" y con su número de documento.
  Esperado    : se rechaza cada una (solo números / muy común / parecida al
                usuario / menos de 8 caracteres). La contraseña no cambia.

CAPA 2 · Almacenamiento seguro de contraseñas (hash)
  Qué protege : que un robo de la base revele las contraseñas.
  Dónde       : Django (PBKDF2-SHA256 con sal, cientos de miles de iteraciones)
  Cómo probar : Shell de Django:
                  from users.models import User
                  print(User.objects.first().password[:40])
  Esperado    : empieza por  pbkdf2_sha256$  ; nunca la contraseña en claro.

CAPA 3 · Bloqueo por fuerza bruta (django-axes)
  Qué protege : probar contraseñas una tras otra.
  Dónde       : settings base.py (AXES_*), users/views.py LoginView
  Cómo probar : 1. Con un usuario de prueba, escriba una contraseña incorrecta
                   varias veces seguidas desde el mismo equipo (límite: 5).
  Esperado    : al llegar al límite (5.º o 6.º intento) responde
                "Demasiados intentos fallidos. Intenta más tarde." durante 1
                hora para ese usuario DESDE ESA IP (otra IP no queda bloqueada,
                así un atacante no puede bloquear la cuenta de otra persona).
                Con la contraseña correcta el dueño sí entra.
  Desbloquear : docker exec heroes_del_corazon_pabon-backend-1 python manage.py axes_reset

CAPA 4 · Límite de peticiones (rate limiting)
  Qué protege : abuso automatizado y saturación de la API.
  Dónde       : base.py REST_FRAMEWORK DEFAULT_THROTTLE_RATES (anon 200/min,
                usuario 1000/min, login 500/min)
  Cómo probar : PowerShell (local):
                  $c=0; 1..210 | % { try { Invoke-WebRequest http://localhost:8001/api/v1/auth/csrf/ -UseBasicParsing | Out-Null } catch { if ($_.Exception.Response.StatusCode.value__ -eq 429) { $c++ } } }; "429 recibidos: $c"
  Esperado    : a partir de la petición ~201 del mismo minuto responde 429
                (Too Many Requests). Al minuto siguiente vuelve a responder.

CAPA 5 · Tokens en cookies httpOnly / Secure / SameSite
  Qué protege : robo de la sesión por un script inyectado (XSS).
  Dónde       : users/views.py _set_auth_cookies; settings AUTH_COOKIE_*
  Cómo probar : 1. F12 > Application > Cookies del sitio.
                2. En la consola escriba:  document.cookie
  Esperado    : access_token y refresh_token tienen HttpOnly = ✓,
                SameSite = Lax y, en producción, Secure = ✓.
                document.cookie NO muestra access_token ni refresh_token.

CAPA 6 · Rotación y revocación de tokens (cierre de sesión real)
  Qué protege : reutilizar un token viejo o robado después de salir.
  Dónde       : SIMPLE_JWT ROTATE/BLACKLIST; RefreshView y LogoutView
  Cómo probar : 1. F12 > Application > Cookies: copie el valor de refresh_token
                   y el de la cookie que empieza por did_ (nombre y valor).
                2. Pulse "Salir" en la app.
                3. curl.exe -i -X POST http://localhost:8001/api/v1/auth/refresh/ --cookie "refresh_token=VALOR; did_XXXX=VALOR"
  Esperado    : 401 "Sesión expirada." — el token quedó en la lista negra.

CAPA 7 · Sesión ligada al dispositivo
  Qué protege : que un token copiado funcione en otro computador.
  Dónde       : users/devices.py, common/authentication.py enforce_device
  Cómo probar : 1. En Chrome, con sesión iniciada, copie el valor de access_token
                   (F12 > Application > Cookies).
                2. En otro navegador (Edge) abra http://localhost:5173/admin/login, F12 >
                   Application > Cookies, cree la cookie access_token con ese
                   valor (sin la cookie did_...).
                3. En la consola de Edge: fetch('/api/v1/auth/me/').then(r => r.status)
  Esperado    : 401 (Device not recognized). Sin la cookie del dispositivo el
                token no sirve.

CAPA 18 (ver abajo) y CAPA 21 (nueva) también son de este grupo.


===============================================================================
 GRUPO B — CONTROL DE ACCESO
===============================================================================

CAPA 8 · Protección CSRF
  Qué protege : que otra página haga acciones en nombre del usuario.
  Dónde       : common/authentication.py enforce_csrf (doble cookie)
  Cómo probar : Consola del navegador (sesión iniciada), petición SIN la
                cabecera X-CSRFToken que la app envía siempre:
                  fetch('/api/v1/auth/password-change/', {method:'POST', credentials:'include', headers:{'Content-Type':'application/json'}, body:'{}'}).then(r => r.status)
  Esperado    : 403 (CSRF Failed). La app normal sí funciona porque envía el token.

CAPA 9 · Control de acceso por rol (RBAC) en el servidor
  Qué protege : que un colaborador use funciones de administración
                aunque manipule el frontend.
  Dónde       : common/permissions.py; permission_classes de cada vista
  Cómo probar : 1. Inicie sesión como Colaborador.
                2. Consola: fetch('/api/v1/users/admin/').then(r => r.status)
                3. Consola: fetch('/api/v1/questions/results-summary/').then(r => r.status)
                4. Escriba en la barra http://localhost:5173/admin/users
  Esperado    : 2 y 3 responden 403; en 4 la app lo devuelve a su inicio.
                El superadmin NO puede enviar evaluaciones (403); el
                coordinador sí, con las mismas reglas que un colaborador.

CAPA 17 · Ventanas privadas, rutas protegidas y "Acceso no autorizado"
  Qué protege : sesiones en ventanas que no dejan rastro en equipos compartidos, y
                que cualquiera abra rutas escribiéndolas en el navegador o en Postman.
  Dónde       : frontend/src/lib/privateMode.js; LoginView (private_mode);
                frontend/nginx/default.conf.template (reglas del frontend);
                frontend/src/lib/appBase.js (la app vive bajo /admin/);
                backend common/navigation.py y common/exceptions.py
  Reglas      : FRONTEND (https://heroesdelcorazon-pabon-1.onrender.com)
                - La app vive SOLO bajo /admin/: /admin/login, /admin/dashboard,
                  /admin/program, /admin/users… /admin redirige a /admin/login.
                - Cualquier otra ruta (/, /login, /program, /index.html…):
                  403 "Acceso no autorizado.".
                - Solo navegadores: sin la cabecera Sec-Fetch-Mode (Postman, curl)
                  también /admin/…, /assets/… y /branding/… dan 403.
                - Solo GET/HEAD: POST, PUT, PATCH, DELETE y OPTIONS dan 405 con el
                  mismo cuerpo y sin cabecera Allow.
                BACKEND (https://heroesdelcorazon-pabon.onrender.com)
                - El panel de Django se movió de /admin/ a /django-admin/.
                - Abrir /api/... en el navegador solo con sesión de /django-admin/
                  (cuenta activa y "staff"); si no, 403 "Acceso no autorizado." y un
                  evento security.direct_navigation en la auditoría.
                - /, /admin/ y cualquier ruta desconocida: el cuerpo único.
                - OPTIONS directo: 405 genérico (ya no describe campos ni métodos).
                - Chequeo de salud de Render: /healthz (frontend y backend).
  Cómo probar : 1. Navegador: abra .../-1.onrender.com/login  y  /  → Acceso no autorizado.
                   Abra .../-1.onrender.com/admin/login → login de la app.
                2. Postman, GET https://heroesdelcorazon-pabon-1.onrender.com/login
                   y /admin/login → 403 JSON "Acceso no autorizado.".
                3. Postman: POST, PUT, PATCH, DELETE y OPTIONS a /admin/login → 405.
                4. Postman: OPTIONS https://heroesdelcorazon-pabon.onrender.com/api/v1/auth/login/
                   → 405 genérico. GET .../admin/ y .../ en el backend → genérico.
                5. Navegador, sin sesión de Django: .../api/v1/auth/me → Acceso no
                   autorizado. Entre a .../django-admin/ (cuenta de createsuperuser);
                   en el inicio, "Endpoints de la API" → se muestra el contenido.
                6. Abra la app en una ventana de incógnito (Ctrl+Mayús+N).
                7. GET /healthz en ambos dominios → {"status": "ok"}.
  Esperado    : lo indicado en cada paso. 6: el login queda deshabilitado.
  Límites     : "Solo navegadores" se decide por la cabecera Sec-Fetch-Mode, que
                Postman puede enviar si se escribe a mano: es disuasión. Lo que
                protege los datos es la autenticación de la API (capas 5 a 9).
                Inspeccionar (F12): ningún sitio web puede impedirlo de verdad. En
                producción se bloquean F12, Ctrl+Shift+I/J/C/K, Ctrl+U y el clic
                derecho fuera de los campos (frontend/src/lib/devtoolsDeterrent.js),
                pero se puede abrir desde el menú del navegador. Es disuasión.
                Navegadores sin Sec-Fetch-Mode (Safari anterior a 16.4) no pueden
                abrir la app.

CAPA 18 · Contraseña inicial con cambio obligatorio
  Qué protege : la contraseña inicial Pabon2026* la conoce todo el mundo.
  Dónde       : common/authentication.py enforce_password_change;
                users/views.py PasswordChangeView; settings DEFAULT_USER_PASSWORD
  Cómo probar : 1. Como superadmin: Usuarios > Crear usuario (sin contraseña).
                2. Salga e ingrese con ese documento y Pabon2026*.
                3. Consola: fetch('/api/v1/questions/evaluations/').then(r => r.json()).then(console.log)
                4. Cambie la contraseña. Intente usar otra vez Pabon2026*.
  Esperado    : 2. Solo aparece "Cambia tu contraseña" (sin menú).
                3. 403 con code "password_change_required" (el bloqueo es del
                   servidor, no solo de la pantalla).
                4. Pabon2026* se rechaza como nueva clave; con una propia, la app
                   abre normalmente.

CAPA 19 · Ciclo de vida de cuentas
  Qué protege : cuentas de personas que ya no trabajan; quedarse sin administrador.
  Dónde       : users/views.py AdminUsersView
  Cómo probar : 1. Usuarios > Administrar usuarios > Inhabilitar (cuenta de prueba).
                2. Intente ingresar con esa cuenta.
                3. Intente inhabilitar su propia cuenta o quitarse el rol de superadmin
                   siendo el único superadministrador activo.
  Esperado    : 2 no puede ingresar. 3 se rechaza: debe quedar al menos un
                superadministrador activo.

 GRUPO D — TRANSPORTE Y NAVEGADOR
===============================================================================

CAPA 11 · Cabeceras de seguridad y CSP
  Qué protege : clickjacking, ejecución de scripts externos, fugas por Referer.
  Dónde       : frontend/nginx/security-headers.conf; settings (CSP, X_FRAME_OPTIONS)
  Cómo probar : curl.exe -sI -H "Sec-Fetch-Mode: navigate" https://heroesdelcorazon-pabon-1.onrender.com/admin/login
                (securityheaders.com no envía Sec-Fetch-Mode: verá el 403, que ya es correcto)
  Esperado    : Content-Security-Policy, X-Frame-Options: DENY,
                X-Content-Type-Options: nosniff, Referrer-Policy,
                Permissions-Policy, Cross-Origin-Opener-Policy.

CAPA 12 · HTTPS obligatorio + HSTS
  Qué protege : interceptar la conexión (Wi-Fi de la clínica, proxies).
  Dónde       : prod.py (SECURE_SSL_REDIRECT, HSTS, cookies Secure); Render
  Cómo probar : curl.exe -sI http://heroesdelcorazon-pabon-1.onrender.com/admin/login
                curl.exe -sI https://heroesdelcorazon-pabon.onrender.com/healthz | findstr /i strict
  Esperado    : la versión http redirige (301/308) a https; aparece
                Strict-Transport-Security.

CAPA 13 · CORS y orígenes de confianza
  Qué protege : que otro sitio web lea la API con la sesión del usuario.
  Dónde       : base.py CORS_ALLOWED_ORIGINS / CSRF_TRUSTED_ORIGINS
  Cómo probar : curl.exe -si -X OPTIONS http://localhost:8001/api/v1/auth/login/ -H "Origin: https://atacante.example" -H "Access-Control-Request-Method: POST"
                Repita con -H "Origin: http://127.0.0.1:5173"
  Esperado    : con el origen atacante NO aparece Access-Control-Allow-Origin;
                con el origen de la app sí.

CAPA 15 · Minimización de información y respuesta única "Acceso no autorizado."
  Qué protege : dar pistas a un atacante: versiones, trazas de error, qué métodos
                acepta una ruta, si una ruta o recurso existe, si una cuenta existe
                o está bloqueada.
  Dónde       : backend/common/exceptions.py GenericApiErrorMiddleware;
                users/views.py LoginView; nginx server_tokens off; DEBUG=False en prod.
  Regla       : en /api/, cualquier endpoint de cualquier módulo y con cualquier
                método (GET, POST, PUT, PATCH, DELETE) responde el MISMO cuerpo:
                  {"detail": "Acceso no autorizado.", "code": "unauthorized_access"}
                cuando: no hay sesión (401), falta permiso o CSRF (403), la ruta no
                existe (404), el método no existe (405), se excede el límite (429) o
                un dato es inválido sin sesión (400). No se envía la cabecera Allow
                ni WWW-Authenticate. Errores 500: "Error interno del servidor." sin traza.
                El código HTTP se conserva (la app necesita el 401 para renovar la
                sesión). Con sesión, los 400 de formularios conservan su mensaje.
                El motivo real queda solo en el log y en la auditoría (capa 23).
  Cómo probar : En Postman (o curl.exe), SIN sesión, pruebe GET, POST, PUT, PATCH y
                DELETE contra:
                  http://localhost:8001/api/v1/auth/login/
                  http://localhost:8001/api/v1/users/admin/
                  http://localhost:8001/api/v1/questions/evaluations/1/
                  http://localhost:8001/api/v1/no-existe/
                Login con un documento que NO existe y con uno que SÍ existe pero con
                clave incorrecta. Revise la pestaña Headers de Postman.
                curl.exe -sI -H "Sec-Fetch-Mode: navigate" https://heroesdelcorazon-pabon-1.onrender.com/admin/login | findstr /i "server x-powered"
  Esperado    : siempre el mismo cuerpo (cambia solo el número: 400/401/403/404/405);
                ambos logins responden idéntico; no hay cabecera Allow; sin versión
                de nginx ni X-Powered-By; nunca la página de depuración de Django.

CAPA 14 · Registro estructurado de auditoría y seguridad (logs)
  Qué protege : poder reconstruir qué pasó (y alertar si hay SENTRY_DSN).
  Dónde       : audit/logging.py, common/security.py log_unauthorized

  Cómo probar : docker exec heroes_del_corazon_pabon-backend-1 sh -c "DJANGO_SETTINGS_MODULE=config.settings.prod DJANGO_SECRET_KEY=corta python manage.py check"
  Esperado    : falla con ImproperlyConfigured (producción no arranca con una clave débil).

 CAPAS NUEVAS (20 A 25) — IMPLEMENTADAS EL 2026-11-19

CAPA 20 · Cierre de sesión por inactividad                       [NUEVA]
  Qué protege : un computador de la clínica que queda con la sesión abierta.
  Dónde       : frontend/src/lib/useIdleLogout.js (usado en Layout.jsx);
                aviso en LoginPage.jsx. Minutos: VITE_IDLE_TIMEOUT_MINUTES (15 por defecto).
                La actividad se comparte entre pestañas; el cierre llama a
                /auth/logout/ (revoca el token en el servidor, no solo la pantalla).
  Cómo probar : Rápido (local): cree frontend/.env.local con
                  VITE_IDLE_TIMEOUT_MINUTES=1
                reinicie .\heroes.ps1 front, inicie sesión y no toque nada ~1,5 min.
                Real: en producción espere 15 minutos sin usar la app.
                Además: trabaje en una pestaña y deje otra quieta.
  Esperado    : vuelve al login con el aviso "Tu sesión se cerró por N minutos de
                inactividad"; en F12 > Network aparece POST /api/v1/auth/logout/.
                Mientras se use una pestaña, la otra NO se cierra.
                Al terminar, borre frontend/.env.local.

CAPA 21 · Revocación de sesiones al cambiar la contraseña        [NUEVA]
  Qué protege : quien conoce la clave anterior y ya tiene una sesión abierta.
  Dónde       : backend/users/sessions.py revoke_all_sessions; PasswordChangeView;
                AdminUsersView (restablecer contraseña)
  Cómo probar : 1. Inicie sesión con la MISMA cuenta en Chrome y en Edge.
                2. En Chrome cambie la contraseña (ícono de llave).
                3. En Edge haga clic en cualquier menú o recargue.
                4. Variante: como superadmin restablezca la contraseña de una
                   cuenta que tenga una sesión abierta en otro navegador.
  Esperado    : 3. Edge queda fuera de inmediato (401) y vuelve al login; Chrome
                   sigue dentro. 4. Todas las sesiones de esa cuenta se cierran.

CAPA 22 · Las respuestas de la API no se guardan en caché         [NUEVA]
  Qué protege : ver datos de la sesión anterior con "Atrás" o desde la caché
                en un equipo compartido.
  Dónde       : backend/common/security.py NoStoreApiMiddleware
  Cómo probar : curl.exe -sI http://localhost:8001/api/v1/auth/me/
                o F12 > Network > cualquier petición /api/ > Response Headers.
  Esperado    : Cache-Control: no-store   y   Pragma: no-cache
                (la raíz "/" y los estáticos no se ven afectados).

CAPA 23 · Auditoría persistente, de solo inserción               [NUEVA]
  Qué protege : poder demostrar quién hizo qué, cuándo y desde dónde (los logs
                de Render se pierden). Nadie puede alterar ni borrar el registro.
  Dónde       : backend/audit/models.py AuditEvent; audit/logging.py;
                common/security.py (eventos "security.*"). Guarda: acción,
                resultado, código HTTP, usuario, rol, IP real del cliente,
                navegador. NUNCA contraseñas, cookies, tokens ni el cuerpo.
  Cómo probar : 1. Haga un login fallido y una acción como superadmin
                   (p. ej. cambiar el rol de una cuenta de prueba).
                2. Shell de Django:
                     from audit.models import AuditEvent
                     for e in AuditEvent.objects.all()[:5]: print(e.created_at, e.action, e.outcome, e.status_code, e.actor_username, e.ip_address)
                3. Intente alterarlo:
                     e = AuditEvent.objects.first(); e.outcome = "x"; e.save()
                     AuditEvent.objects.all().delete()
                4. Con una cuenta de Django staff: /django-admin/ > Auditoría >
                   Eventos de auditoría.
  Esperado    : 2. Aparecen login.post failure, security.wrong_password blocked,
                   admin-user-detail.patch success con usuario e IP.
                3. AppendOnlyError en ambos casos.
                4. Se puede buscar y filtrar, pero no hay botones de agregar,
                   editar ni borrar.

CAPA 24 · Validación de archivos subidos                         [NUEVA]
  Qué protege : ejecutables renombrados, archivos gigantes o "zip bombs" en
                Cargar datos / Importar evaluaciones o respuestas.
  Dónde       : backend/common/uploads.py validate_upload; UPLOAD_MAX_MB (5)
  Cómo probar : En Cargar datos > Cargar personal suba:
                  a) un .pdf o .exe
                  b) un .txt renombrado a .xlsx
                  c) un .xlsx de más de 5 MB
                  d) la plantilla real ("Descargar plantilla") con una fila
  Esperado    : a) "Tipo de archivo no permitido."  b) "El archivo no es un
                Excel válido (.xlsx)."  c) "El archivo supera el máximo de 5 MB."
                d) se carga normalmente.

CAPA 25 · Escaneo de vulnerabilidades en dependencias            [NUEVA]
  Qué protege : librerías con fallas de seguridad conocidas (CVE).
  Dónde       : .github/workflows/backend-ci.yml (job dependency-audit, pip-audit)
                .github/workflows/frontend-ci.yml (job dependency-audit, npm audit)
  Cómo probar : Local:
                  docker exec heroes_del_corazon_pabon-backend-1 sh -c "pip install -q pip-audit && pip-audit -r requirements/prod.txt"
                  cd frontend; npm audit --omit=dev
                En GitHub: pestaña Actions tras un push a main.
  Esperado    : backend "No known vulnerabilities found".
                Al implementarla encontró 7 avisos: djangorestframework 3.18.0
                (3 CVE) y daphne 4.2.1 (4 avisos); se actualizaron a 3.18.2 y 4.2.2.
                frontend: 1 aviso ALTO en "xlsx" (SheetJS) sin arreglo en npm.
                Solo afecta a LEER archivos Excel; esta app solo los GENERA
                (exportar resultados, plantilla), así que no es explotable aquí.
                El CI falla solo con severidad crítica. Ver pendiente P4.
